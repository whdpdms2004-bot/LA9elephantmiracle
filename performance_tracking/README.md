# performance_tracking — 제출 모델 성능 관리

이 폴더가 앞으로 **제출본 단위 모델 관리**의 단일 출처다. 여기 규약대로 등록되지
않은 모델은 앙상블 후보로 쓰지 않는다.

### 규칙 1 은 왜 바뀌었나 — 관문의 70% 가 성능이 아니었다

|  | 2022 | 2024 |
|---|---:|---:|
| F 기저율 | **0.7087** | 0.4593 |
| R 기저율 | 0.5037 | 0.4897 |

**2022 는 F 와 R 의 기저율이 0.2 나 벌어져 있고 2024 는 거의 같다.** BSS 는 기저율로
정규화되므로, 2022 를 `all` 로 재면 점수의 상당 부분이 모델 성능이 아니라 **그 폴드의
`game_type` 구성**을 재게 된다. `sj_grid_w060` 이 `2022 all 2,490.2` 인데
**`2022 R` 만 보면 740.7** 이다 (2024 는 903.0 → 921.4 로 오히려 오른다).

그래서 **관문 시즌(2022·2023)은 `R` 만 본다.** 2024 는 두 부분군의 기저율이 붙어 있어
`all` 로 봐도 왜곡이 없고, F 가 헤드룸의 대부분이라 `all` 로 봐야 한다.
근거 전문은 [`group_by_perform/RESULTS.md`](group_by_perform/RESULTS.md) §1.

> **2023 은 새로 들어온 관문 시즌이다.** 지금 등록 모델 중 2023 예측이 있는 것은
> `ye_hand` 뿐이라, 나머지는 그 관문이 **미확인**으로 뜨고 판정이 `조건부채택` 이 된다.
> 확보되면 자동으로 관문에 들어온다. **`val/<name>_2023.csv` (≤2022 학습) 를 채우는 것이
> 지금 등록부의 가장 큰 공백이다.**
>
> 주의 — "fold 2023 은 쓸 수 없다" 는 기존 기록은 **결합 가중을 2023 에서 *적합*하면
> 발산한다**는 뜻이다 (`cb +2.854 / ft −2.328`). **2023 에서 *평가*하는 것과는 다른
> 이야기**이므로 이 개정과 충돌하지 않는다.

## 1. 폴더 구조

```text
performance_tracking/
├── README.md                  # 이 파일 — 규약
├── results.csv                # 등록부 (모델 1개 = 1행)
├── templates/
│   └── MODEL_TEMPLATE.md      # 규칙 2 의 MD 서식
├── tools/
│   ├── score_val.py           # 규칙 1 채점 + results.csv 등록
│   └── corr.py                # 규칙 3 상관계수 / 블렌드 스캔
├── models/
│   ├── <name>.md              # 규칙 2 — 모델 구성
│   ├── <name>.zip             # 규칙 4 — 제출 zip (script.py + requirements.txt + model/)
│   └── <name>/                # 규칙 4 — 학습 스크립트 전문 (재현 가능한 전부)
└── val/
    ├── <name>_2022.csv        # 규칙 3 — val 예측
    └── <name>_2024.csv
```

`<name>` 은 **제출 zip 의 파일명(확장자 제외)** 과 글자 하나까지 같게 쓴다.
`.md` / `.zip` / 폴더 / val 예측 4곳의 이름이 어긋나면 도구가 등록을 거부한다.

### zip 양식 (규칙 4 — 제출본과 동일)

```text
<name>.zip
├── script.py          # 추론 전용. 학습 코드 금지 (cowork/RULES.md §0-7)
├── requirements.txt
└── model/             # 가중치·LUT·params.json
```

학습 코드는 zip 에 넣지 않고 `models/<name>/` 에 둔다. 그 폴더만 있으면
zip 의 `model/` 을 처음부터 다시 만들 수 있어야 한다 (경로·시드·데이터 as-of 포함).

## 2. val 예측 파일 규격 (규칙 3)

`val/<name>_2022.csv`, `val/<name>_2024.csv` — 컬럼 2개, 헤더 필수.

```csv
row_id,pred
TRAIN_1221586,0.5123
```

- `row_id` 는 `data/train.csv` 의 `row_id` 문자열 그대로 (`TRAIN_...`). 정렬 순서는 무관하다 (도구가 join 한다).
- `pred` 는 **최종 `control_success` 확률** 하나. way 확률(middle/reverse/outside)이나
  로짓을 넣지 않는다 — 평균이 0.35~0.65 밖이면 도구가 거부한다.
- 해당 시즌의 `control_success` 비결측 행을 **전부** 담는다. 결측·중복·누락은 오류다.
- 여기 저장하는 예측은 **그 시즌을 학습에서 제외하고** 낸 값이어야 한다.
  2022 예측을 2022 가 학습에 들어간 모델로 내면 규칙 1 의 비교가 무의미해진다.

## 3. 채점 (규칙 1)

```bash
python performance_tracking/tools/score_val.py <name>
```

- 대회 공식 지표: `Score = 100000 x (1 - Brier / (r(1-r)))`, `r` 은 그 부분군 실제 기저율.
- 시즌마다 `all / R / F` 와 월 블록(early 3-5, mid 6-7, late 8-10)을 함께 낸다.
  `game_type` 은 2022→2023 에 구조적 단절이 있어(`cowork/sj/three_way/VALIDATION_POLICY.md` §1.1)
  전체 BSS 하나만 보면 F 부분군이 만든 착시를 그대로 채택하게 된다.
- **채택 판정** (2026-08-28 개정): 기준 모델 대비

  | 시즌 | 부분군 | 조건 |
  |---|---|---|
  | 2024 | `all` (R+F) | **올라야 한다** — 주 판정 |
  | 2023 | `R` | 떨어지면 안 된다 — 관문 |
  | 2022 | `R` | 떨어지면 안 된다 — 관문 |

  기준 모델은 `--baseline <name>` 으로 지정한다. 2023 예측이 없으면 그 관문만
  **미확인**으로 두고 판정이 `조건부채택` 으로 나온다 — 통과로 세지 않는다.
- 통과하면 `--register` 로 `results.csv` 에 한 행 append 한다 (기존 행은 수정하지 않는다).

## 4. 앙상블 상관 (규칙 3)

```bash
python performance_tracking/tools/corr.py                      # 등록된 전 모델 상관 행렬
python performance_tracking/tools/corr.py -m a -m b --blend    # 두 모델 가중 스캔
```

상관은 **예측 확률**과 **오차(pred - y)** 두 축으로 낸다. 확률 상관이 0.99 여도
오차 상관이 낮으면 결합 이득이 남아 있다.

> 결합층 상수(가중치·온도)는 **행 CV 로 고르지 않는다.** fold(N-1) 에서 적합하고
> fold(N) 에서 동결해 판정한다 — 행 CV 로 고른 상수는 시즌 전이에서 뒤집힌 실측이 있다.

## 5. 등록 절차 체크리스트

1. `models/<name>/` 에 학습 스크립트 전문을 넣는다.
2. `models/<name>.zip` 을 제출 양식대로 만든다 (`script.py` 는 추론 전용).
3. 2022·2024 를 각각 학습에서 빼고 예측을 내 `val/<name>_2022.csv`, `val/<name>_2024.csv` 로 저장한다.
4. `templates/MODEL_TEMPLATE.md` 를 복사해 `models/<name>.md` 를 채운다.
5. `score_val.py <name> --baseline <기준> --register` 로 채점·등록한다.
6. Public 점수가 나오면 `results.csv` 의 해당 행 `public` 칸과 `.md` 의 실측 표를 갱신한다.

## 8. 부분군 진단 — `group_by_perform/`

3절의 채점은 `all / R / F` 와 월 블록까지다. **어느 상황에서 잃는지**는
그것만으로 안 나온다. `group_by_perform/` 이 그 좌표를 낸다.

```bash
python performance_tracking/group_by_perform/build_axes.py     # 축 파생 (캐시)
python performance_tracking/group_by_perform/group_score.py    # 모델 x 축 x 구간
python performance_tracking/group_by_perform/recal_transfer.py # 2022 적합 -> 2024 판정
python performance_tracking/group_by_perform/report.py         # RESULTS.md 생성
```

규약 전문은 [`group_by_perform/PLAN.md`](group_by_perform/PLAN.md),
결과는 [`group_by_perform/RESULTS.md`](group_by_perform/RESULTS.md). 네 가지만 여기 옮긴다.

### ★ 1회차 결과가 이 규약 자체를 건드린다 (2026-08-28)

**2022 의 F 기저율은 0.7087, R 은 0.5037 이다. 2024 는 F 0.4593 · R 0.4897 로 격차가 없다.**
그래서 0절 규칙 1 의 **"2022 비하락" 관문은 70% 가 `game_type` 을 재고 있다** —
`sj_grid_w060` 이 `2022 all 2,490.2` 인데 `2022 R만 740.7` 이다 (2024 는 903.0 → 921.4 로 상승).

**채택됨 (2026-08-28).** 0절 규칙 1 을 개정했다 — 관문 시즌은 **`R` 만** 보고,
**2023 이 관문 시즌으로 새로 들어왔다.** 근거는 `group_by_perform/RESULTS.md` §1.
도구(`tools/common.py` · `tools/score_val.py`)에도 반영돼 있다.

#### ★ 개정 직후 재채점에서 나온 것 — 등록부와 모델 카드가 어긋난다

새 관문으로 등록 자산을 다시 돌렸더니 **`results.csv` 의 `채택` 판정 두 개가
재현되지 않는다.** 등록된 `val/` 예측으로 `sj_grid_w060` 기준 재계산하면:

| 모델 | 2024 all | 2022 all (구 관문) | **2022 R (새 관문)** | 등록 판정 | 재계산 |
|---|---:|---:|---:|---|---|
| `sj_e2var` | **−25.6** | −5.7 | −2.3 | 채택 | **기각** (2024 미상승) |
| `sj_stdmlp` | +13.0 | **−137.1** | **−72.6** | 채택 | **기각** (관문 하락) |

원인은 **기준 모델의 계기가 다르다는 것**이다. 두 `.md` 는 "배포 순서 재현" 으로
기준을 `2024 893.7 / 2022 2,342.1` 이라 적었는데, 등록된
`val/sj_grid_w060_{2024,2022}.csv` 는 `903.0 / 2,490.2` 다. 2022 에서 **148 이 벌어진다.**

**둘 중 하나는 틀렸고 아직 어느 쪽인지 모른다.** 규칙대로 기존 행은 손대지 않았다.
`val/sj_grid_w060_2022.csv` 가 어떤 구성으로 만들어진 예측인지 확인하는 것이 먼저다.

이건 새 관문이 만든 문제가 아니다 — **구 관문(`2022 all`)으로 재도 `sj_stdmlp` 은
−137.1 로 기각**이다. 관문을 `R` 로 바꾼 것과 무관하게 원래 어긋나 있었다.
`sj_stdmlp` 의 Public 이 예상 1091~1099 에 못 미치고 **+1.68** 에 그친 것과 방향이 같다.

### AUC 와 BSS 를 항상 같이 본다

`BSS` 하나로는 **변별력**이 나쁜 건지 **보정**이 나쁜 건지 갈리지 않는다.
`AUC` 가 같이 떨어지면 보정으로 못 고친다. `AUC` 는 멀쩡한데 `bias` 만 크면
구간 상수 하나로 고쳐진다.

### `deficit` 가 구간 비교의 유일한 기준이다

    deficit = 100000 x (n/N) x brier / (r_all(1-r_all))
    Sigma_구간 deficit  =  100000 - BSS_all      (항등식)

구간별 `bss_local` 만 보면 **작고 나쁜 구간**에 속는다. `deficit` 는 합이
전체 결손과 같으므로 "이 구간이 먹은 몫"을 그대로 읽는다.

### 구간 처방은 `self` 로 판정하지 않는다

구간별 보정을 그 구간에서 골라 그 구간에서 재면 반드시 좋아 보인다.
4절 끝의 규약과 같다 — **2022 에서 적합·동결하고 2024 에서 판정한다.**
`shift_gain_self` 는 참고값이고, 채택 근거는 `shift_gain_xfer` 뿐이다.

### 축을 만들 때 복원한 것 — `game_uid`

`data/train.csv` 에는 경기 ID 가 없다. 파일 시간순 + 팀쌍 전환 + 이닝 감소로
복원했고, 시즌당 796~824경기 · 경기당 중앙 300구 · 등판당 중앙 19구(p90 92)로
검증했다. 투수 등판 단위 축(A3·A12)은 전부 여기서 나온다.
